## 可行动的代码问题

P1 表示应优先修复的核心稳定性问题，P2 表示需在日用交付前解决的问题。以下除明确标注的合成复现外，属于源码确认的缺陷路径，触发概率与实际影响仍须目标环境验证。

### 1. P1：媒体重新配置存在新旧采集序列碰撞

- 入口：麦克风共享时开关摄像头、切换媒体设备，或再次配置仍启用的麦克风。
- `MediaBridge/main.m:419` 停止旧采集，但 `RVCapture.stop` 不清除 `RVWriter` 已排队的旧媒体；`configure` 中 `startRunning` 在 `:433` 状态 ACK 入队之前启动新的采集，新的音频序号从零开始。
- `TBMediaBridge.swift:71` 发请求时先重置序列门禁；`:125` 即使 `microphoneEnabled == false` 仍先校验音频连续性。因此 ACK 前收到旧音频后再收到序号归零的新音频，会抛出 `invalidPacket` 并关闭整个媒体连接。JPEG 也有类似的递增序列约束。
- **合成复现通过**：实际 `RVWriter` 与 `RVCapture.stop` 保留旧 PCM，并允许旧 PCM、新 PCM、ACK 的入队顺序；从当前源码提取的 Swift 协议门禁拒绝 `9600 → 0`。
- 建议：建立明确的配置代际／请求标识与 ACK 屏障，清理尚未发送的旧媒体，保证新代媒体只在 ACK 后发布；等待 ACK 的样本处理须与代际规则一致。补充“麦克风运行时开关摄像头”的回归，而不只测试独立 gate.reset。

### 2. P1：网络显示与 HDMI 待命会同时播放声音

- `RescueReceiver/main.m:186` 创建局部 `AVCaptureAudioPreviewOutput` 并固定 `volume = 1.0`，没有保存可供仲裁修改的引用。
- 网络状态处理 `:279` 和呈现／电源仲裁 `:320` 都不调整 HDMI 音频。Network Receiver 首帧后又会启用 SDL 音频（`TBReceiverC/src/main.c:1064`）。
- 因此 HDMI 与网络均有声音时，画面虽然优先显示网络输入，扬声器仍可能混播两路，或播放同一来源的两份延迟声音。窗口遮挡不会让 AVFoundation 音频静音。
- 建议：让扬声器路由跟随有效画面优先级；保留 HDMI 采集待命，网络有效时静音救援预览，网络失效后恢复，并处理音频设备断开／重连。

### 3. P1：Sender → iMac 扬声器音频绕过有界发送保护

- `TBDisplaySenderService.swift:2696` 每个音频回调都会创建 MainActor 任务，缺少待处理任务／音频时长上限。
- `:3514–3524` 音频直接进入 `NWConnection.send`，没有待发送字节／包数限制；完成回调忽略错误。视频的 `TBVideoSendGate` 不保护此路径。
- 主线程忙或链路停顿时，音频可继续排队；即便视频队列已限制，音频仍可能造成内存积压、过期声音和共享 TCP 的延迟。Receiver 的 150ms 音频环限制无法约束 Sender 和网络框架内的排队。
- 建议：对音频从回调到发送完成的全部异步边界设定时长／字节上限，拥塞时明确丢弃或结束对应会话；处理发送错误，验证持续播放音频时的链路暂停与恢复。

### 4. P2：Rescue 重复隐藏鼠标，计数不平衡

- `RescueReceiver/main.m:345` 在每秒 tick 的活动路径调用 `CGDisplayHideCursor`；无信号时 `:352` 每秒只调用一次 `CGDisplayShowCursor`，退出时 `:406` 最多调用一次，且判断的是 HDMI `showingVideo`。
- 本机 SDK 的 `CGDirectDisplay.h` 明确注明 Hide 增加隐藏计数、Show 减少计数并在零时显示。持续活动会不断累积计数，转入无信号状态后不能及时恢复鼠标；仅有网络信号时退出清理也未覆盖正确状态。
- 建议：用独立的 cursorHidden 状态，只在状态转换时 hide/show，并在正常退出时平衡本进程的隐藏操作。无需启动真实图形界面即可测试调用次数。

### 5. P2：Receiver 控制消息的同步发送会冻结显示主循环

- `TBReceiverC/src/main.c:1408` 的 `send_all` 在 EAGAIN 时同步重试最多 2 秒；它与解码、绘制、状态通知共用事件循环。
- 输入事件发送 `:1655` 忽略其返回值，失败后仍可能继续发送下一条事件。部分包已写出后继续使用同一连接，还可能破坏对端的包边界。
- **合成复现通过**：对非阻塞 socketpair 填满发送缓冲，调用当前源码的 `send_all`，返回前阻塞 **2000ms**。没有初始化 SDL、输入注入或窗口。
- 建议：改为有界的非阻塞控制发送队列；发送失败及时终止会话，避免在同一轮处理多条事件时累积长时间阻塞。

### 6. P2：仅有线连接的产品约束未落实到全部连接路径

- `TBDisplaySenderManager.swift:937` 按 `en* / eth* / bridge*` 名字接受接口，没有核对真实接口类型、链路速率；此规则不能区分 macOS 的 Wi-Fi 与 Ethernet。
- 独立媒体连接 `TBMediaBridge.swift:27` 直接使用默认 `.tcp`，未绑定显示会话选择的本地接口，也未沿用显示路径的 link-local interface scope 处理。主显示连接已经有对应处理（`TBDisplaySenderService.swift:1492`）。
- 因此“网络连接”仍可能选择无线接口，独立摄像头／麦克风在多接口或雷电 link-local 环境下也可能走不同路由或连接失败；按 900Mbps 估算容量不能代替检查实际链路。
- 建议：基于真实接口类型落实 Ethernet／Thunderbolt 门禁；独立服务复用已确认的接口与地址作用域，并清楚提示不足千兆的链路。

### 7. P2：安装升级失败可能让已存在的 HDMI Rescue 停留在停止状态

- `scripts/install_receiver.command:38–41` 先卸载所有 LaunchAgent，随后才复制应用、生成配置和验证 plist。
- 可选媒体的复制／Python 配置步骤 `:48–58` 或其它中间步骤失败时，`set -e` 直接退出；直到 `:133` 才启动 Rescue，期间没有失败恢复机制。
- 可选模块的安装错误因此能使原本运行的核心显示／救援服务停掉，违背优先保住核心功能的交付目标。还应在干净 Catalina 环境核验新增 `/usr/bin/python3` 运行时依赖，不假设开发机拥有的工具在目标机存在。
- 建议：先在暂存区完成验证，再替换与重启核心；失败恢复旧服务；可选媒体独立报告失败。增加已有安装升级失败的文件／服务模拟回归。

## 对照产品目标仍待补齐的部分

1. **显示工程与验收**：25–35ms 只是目标。尚缺完整帧年龄观测、实际硬解确认、跨 socket 批次积压恢复、刷新同步验证、明确的颜色／范围与 ICC 策略、扬声器时钟及音画同步。Receiver 当前固定 BT.709 转换且创建 renderer 时未启用 VSync；这说明需要测量与完善，不能直接断言真机一定撕裂或偏色。默认档仍是 1440p30，专用 1080p60 低延迟档须手选，缺少面向目标 iMac 的能力推荐流程。
2. **摄像头／麦克风完整交付**：系统扩展与 HAL 源码已有，尚未完成签名激活、重启安装／卸载、FaceTime 等第三方应用识别。初版 720p20；媒体故障后手动恢复、设备列表热更新和消费端按需采集联动仍待完成。
3. **安装与日用闭环**：当前安装主要依赖脚本和人工授权／配对。需要统一的首次设置、明确可恢复的错误、真实安装状态检测、单台解除配对／轮换，以及完整升级与卸载验收。媒体与显示的地址／接口管理仍分散。
4. **并发负载与长期运行**：应用内带宽预算已有，系统对 SMB／其它进程的固定保证没有。应先做共享瓶颈下的拥塞、拔线、进程崩溃、睡眠唤醒、长时间 CPU／内存与音画同步验收；是否需要系统限流应依目标负载和测量结果决定。
5. **交付状态一致性**：现有 Test ZIP 未包含当前工作树新增媒体和生命周期能力；HANDOFF、Testing 等文档同时保留“已实现”和“仍待实现”的旧状态。正式测试入口需对应同一套双端源码与构建，避免拿旧包验证新代码。
6. **HDMI 有效信号识别**：现在依赖 UVC 帧流判断有效信号；采集卡无 HDMI 输入仍输出黑帧时，可能永远判定有输入并保持亮屏。已被路线图明确记录，应在目标 MS2130S 验证后决定是否补专用信号检测。

这些是剩余功能与证据缺口，不全部属于已复现的运行时 Bug。SSH、Server Mode、USB、120Hz 等扩展继续排在核心稳定性之后；取消加密的决定继续遵守。

## 水平评价与建议顺序

优点是模块故障边界清楚：Catalina Receiver、独立 Rescue、媒体服务与存储监视分开；已有配对认证、有限视频／媒体队列、原生卸载防越界与合成回归，文档也基本如实区分源码与实测。作为个人工程项目，基础较扎实，已超过仅能演示画面的原型。

主要短板是跨模块的运行闭环：视频队列有界不代表音频也有界，画面仲裁不代表声音也仲裁，单次媒体采集通过不代表重新配置正确，单个服务独立不代表安装失败能保住 Rescue。这些问题比增加功能按钮更直接影响显示器体验。

建议顺序：先修媒体代际、双路声音仲裁、音频有界发送；随后修鼠标计数、Receiver 发送阻塞、有线接口管理与安装失败恢复；形成同步的新双端测试包；最后按授权完成目标 Catalina／现代 Sender 的性能、稳定性与虚拟设备验收，再推进高级扩展。
