# ReVoyage 再次审查与优化建议

日期：2026-10-03。审查最新工作树及 Test8；目标为用户已确认的 iMac 21.5 Late 2015 非 Retina、1920×1080、Catalina 10.15.7。没有启动 ReVoyage 应用、模拟器、目标机、物理采集或系统设备激活。

结论：核心架构已有基础，仍处于尚未完成目标硬件验收的 Alpha。此前七项修复和 D-020 Rescue Lock 已在代码中，不列为缺失；1080p 面板适配、可靠亮度、带宽分配落地、音画质量与日用验收仍是主要差距。本轮没有修改生产代码。

## 优先修正：真实面板与 1× 显示

**P1，当前问题：**Receiver `src/main.c:2128` 仍固定报告 5120×2880、2560×1440 HiDPI，与实际 1080p 内屏不符。Sender `TBDisplaySenderService.swift:1221` 的初始预设仍是 1440p30；目标机器不应默认走额外缩放。

**新增确认，1×适配缺口：**Sender `TBVirtualDisplayModeSize` 的 backing 尺寸固定乘 2（`ReceiverBackedVirtualDisplaySession.swift:15`），`renderMatchedDisplayMode` 又固定把捕获尺寸除以 2（`TBDisplaySenderService.swift:352`）。因此只把 Receiver 改成正确的 `hiDPI:false`，还不能保证“匹配渲染到视频流”正确：1080p 流的匹配模式会变成 960×540，而 1×屏幕实际仅渲染 960×540，需要再放大。当前 Receiver 总报告 Retina，尚未触发这条正确非 Retina 配置下的路径；这是修复面板报告时必须一并处理的缺口。

建议：以真实内屏的原生模式和身份生成 profile；把物理面板、逻辑桌面、backing 像素和编码尺寸分开。缩放关系统一取自 `hiDPI`，增加 1×／2×覆盖；默认档按接收器能力选择，此机器优先 1080p60 H.264。固定 218 PPI 的物理尺寸也应跟随真实面板信息。不能直接拿临时 SDL 窗口大小当物理面板能力，也不应将整个产品硬编码为只支持这一台 1080p iMac。

## 优先修正：亮度命令可靠性

**P2，已有问题仍在：**`display.c:1536` 忽略背光调用的结果，遍历全部活动显示器而非选定内屏；Sender 只有请求值，无实际亮度回读、能力声明或自动亮度同步。设置同步的成功 ACK 不能证明背光已经改变。

**新增复现：**独立亮度命令 `main.c:1425` 忽略解析是否成功，缺少 `level` 或类型错误时仍调用亮度设置，值为默认 100%；`extract_json_double_field` 使用 `strtod`，没有在该命令路径检查有限数值，因此非法 JSON 的 `NaN` 也会传入背光接口。版本化设置同步路径已经检查 `isfinite`，独立亮度命令应使用同等校验。该问题发生在已认证命令路径，不是配对绕过。

建议：无效命令无副作用；限定 0…1 且数值有限，返回明确失败。锁定 iMac 内屏、检查执行结果并回读，区分请求、保存和实际状态。自动模式由 iMac 本地传感器／系统执行，Sender 同步能力与实际值；无关设置同步避免重复改写亮度。亮度 0 不替代 `MANUAL_DISPLAY_OFF`。

## 带宽 UI：已确认，执行层尚未接入

界面定稿见 [BandwidthAllocationUI.md](BandwidthAllocationUI.md)。当前生产代码只有按接口的视频准入预算和有限发送队列，没有六通道双向分配、通道间借用或原生 SMB 的硬盘／SD 独立限速。

源码策略与预览还需统一：`TBVideoBandwidthBudget` 对保存容量再保留 15%，并为每路视频增加 5 Mbps 辅助预算。容量设为 900 Mbps 时，准入总预算实际是 765 Mbps；预览则展示每方向 900 Mbps 可分配。两者在当前阶段不构成生产回归，因为预览尚未接入，但不能直接接上滑块后混用两种定义。

建议：先建立统一的双向容量、协议／控制余量与通道配额模型，明确“基础份额可借用”与“固定上限”的差别。将视频、音频和反向媒体各自接入实际发送控制，并用执行结果确认生效。硬盘与 SD 使用系统 SMB，不受现有视频预算约束；先验证可以怎样真正分开控制，再启用对应执行入口。示例数字、界面 MB/s 和余量均不等于物理设备吞吐保证。

## 声音故障隔离与性能观测

**优化建议，现有取舍：**Sender `TBDisplaySenderService.swift:2784` 的音频过期、队列超额或发送失败会停止整个显示会话。它能避免旧音频持续积压，是此前有界队列修复的一部分；但视频与音频共用 TCP，声音拥塞仍可能引发网络画面切换。不能仅删除失败处理，否则积压或已提交数据问题会重新出现。

先记录视频／音频发送积压与故障原因，再评估音频独立传输或可验证的调度方案。音频暂时不可用应能明确静音／提示，基础视频和 Rescue 保持可用；真正网络故障仍进入 Rescue Lock。

帧健康时间当前记录 SDL 提交时刻，不是源画面的采集年龄。已缓存的旧帧刚提交，也会被视为最近有呈现。这不违反现有“呈现仍有进展”的状态检查，但不能证明画面已经追上实时输入。

建议先补实际硬解状态、帧序号／采集与呈现信息、编码／解码／发送积压、帧年龄及丢帧原因。跨机器时钟需有对应测量方法，不能直接相减当作单向延迟。随后用数据决定跨批次恢复策略、刷新同步、颜色范围／BT.709 等元数据与 ICC 映射；25–35 ms 仍是工程目标。

- Rescue 的锁存／人工关屏已实现并通过本地替身测试；健康模式自动节能、Sender display-sleep 同步、本地离线人工控制和 Catalina 真实电源效果仍待交付。

- Camera／Microphone 的源码不等于第三方应用已能选用：开发者团队签名、系统激活、真实采集、睡眠恢复与通话应用兼容性尚未验收。
- Git 最新提交仍为 Test6 阶段 `7c7b113`；Test7/8、共享电源协议、Media Bridge 和虚拟设备等大量新增源码尚未纳入版本记录。建议整理私有里程碑提交及构建清单，确保换设备能恢复当前功能；不发布或推送公开仓库。本轮未提交或推送。

## 推荐交付顺序

1. 真实 1080p 面板、1×显示逻辑和可靠亮度命令；通过协议／模式回归后再构建对应测试版。
2. 双向带宽模型和已确认界面接入；按真实执行能力逐个启用通道，优先保护显示／声音。
